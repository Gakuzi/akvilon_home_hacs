# ADR-002: Непрерывный живой видеопоток камер через shared RTP-сессию

- **Статус:** принято
- **Дата:** 2026-10-10
- **Ветка:** `feature/video-go2rtc`

## Контекст

ADR-001 дал покадровый захват (`hub.camera_frame`): openCamera → cameraSettings →
подписочный пакет `b"\x00\x00"+videoToken` → RTP/H.264 → JPEG через ffmpeg.
Для непрерывного «живого окна» (HA `stream` / карточка без обновления по таймеру)
этого мало: каждый кадр — это отдельная openCamera→closeCamera-сессия, что
дорого и упирается в лимит активных видео-сессий сервера здания.

SPEC-002 требует непрерывный поток на базе `rtp_stream`, при этом:
- не ломать покадровый захват (`camera.async_camera_image`, `/snap/`, Recorder);
- не ронять HA при отсутствии go2rtc/ffmpeg (graceful-деградация к кадру);
- соблюдать лимит одновременных видео-сессий сервера.

## Решение

Добавлен **менеджер живых RTP-сессий** в `rtp_stream.py` (`LiveStream` +
`StreamManager`), который держит ОДИН UDP/RTP-приёмник на камеру и шарит его
между всеми зрителями:

1. **`LiveStream.run(on_frame, ...)`** — продлеваемый вариант `grab_jpeg`: в цикле
   открывает свежий сокет, шлёт подписочный пакет, собирает IDR-кадры и зовёт
   `on_frame(jpg)`. По таймауту окна (`retry_interval`) сессия переоткрывается —
   это и есть «переустановка сессии» при уходе UDP-потока. Останавливается по
   `stop`-событию или по истечении `total` (TTL).
2. **`StreamManager`** — потокобезопасный пул сессий:
   - **refcount:** несколько зрителей одной камеры получают `subscribe`/`unsubscribe`
     и шарится один сетевой источник; последний зритель закрывает сессию и
     отправляет `closeCamera` (колбэк `on_release` → `hub._close_camera_session`);
   - **лимит сессий:** ведётся бюджет `max_concurrent`; при исчерпании выселяется
     самая давняя сессия (LRU-эвикция с тем же `on_release`), чтобы не копить
     активные видео-сессии на сервере;
   - **UDP-таймаут:** сессия переоткрывается через `retry_interval`, если поток
     замолчал.
3. **`viewer.py`** — веб-панель использует `StreamManager` для `/mjpeg/<cam>` и
   `force`-захвата снапшотов (`_live_frame`): один источник на камеру вместо
   повторяющихся одиночных openCamera. Менеджеру передаётся `on_release`
   (`hub._close_camera_session`), чтобы после последнего зрителя освобождать
   видео-сессию на сервере.
4. **`camera.stream_source()`** — возвращает MJPEG-URL живото окна
   (`<viewer_base>/mjpeg/<cam_id>`) для HA `stream`, когда viewer запущен. Если
   viewer не запущен (или go2rtc/ffmpeg недоступны) — возвращает `None`, и HA
   gracefully возвращается к покадровому `async_camera_image`.

### Почему не go2rtc-зависимость

go2rtc — внешний аддон, решение о его использовании принимает владелец. Этот
подход делает непрерывный поток **без** go2rtc: HA `stream` принимает MJPEG-URL,
который ffmpeg читает как `-f mjpeg -i http://...`. Отсутствие go2rtc/ffmpeg не
сломает интеграцию: `stream_source()` вернёт `None`, и она останется в покадровом
режиме.

## Последствия

- Живое окно в viewer и HA `stream` работает непрерывно без обновления по таймеру.
- Покадровый захват (`camera_frame`, `/snap/`, Recorder) не изменён и работает как
  раньше.
- Лимит активных видео-сессий сервера соблюдается (бюджет + LRU-eвикция +
  closeCamera на release).
- Все сетевые/блокирующие операции живого потока выполняются в фоновых потоках
  менеджера, а не на event loop HA.
- Публичный контракт `hub.camera_frame(cam_id, timeout)` не менялся.

## Ограничение

Вне зоны этой ветки осталось добавление `hub.camera_stream(...)` в `coordinator.py`
(файл закреплён за другим агентом). Менеджер живых сессий живёт в `rtp_stream.py`
и подключается через `camera.py`/`viewer.py`, что покрывает цель SPEC-002 без
правки ядра хаба.
