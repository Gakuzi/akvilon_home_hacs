# CONTRIBUTING.md — Как вносить изменения в Akvilon InHome

> Как принимаются изменения, ветки, проверка и что попадает в релиз. Короткая
> версия важных процессов уже есть в `AGENTS.md` (карта) и подробная политика
> релизов — в `RELEASE_POLICY.md`. Сначала прочитай их.

## 1. Проект и где что лежит

`Akvilon InHome` — интеграция для Home Assistant (UDP-протокол к серверу здания).
Код — в `custom_components/akvilon_home/`. Инструкции для агентов — внутри
`custom_components/akvilon_home/AGENTS.md`, там же логика протокола и важные gotcha.

Есть **два репозитория**:

| | Приватный (разработка) | Публичный (HACS) |
|---|---|---|
| URL | `git@github.com:Gakuzi/akvilon_home.git` | `github.com/Gakuzi/akvilon_home_hacs` |
| Назначение | feature/`м`develop`, обкатка | чистые релизы |

Этот репозиторий — **публичный**. Он получает код ТОЛЬКО через
`scripts/sanitize.sh` (очистка личных данных) + `scripts/release.sh` (тег/релиз).
Вручную код тут не редактируется — подробности в `RELEASE_POLICY.md`.

## 2. Политика веток

- `main` — стабильная версия. Попадает ТОЛЬКО проверенный код после слияния.
- `develop` — интеграционная ветка разработки.
- `feature/*` — под задачу/фичу, создаются от `develop`, **один человек/агент = одна ветка**.
- `hotfix/*` — срочные исправления от `main`.
- **Никогда напрямую в `main`/`develop`** — только через feature-ветку и ревью/слияние.

## 3. Как работаем

1. Читаем обязательный порядок в `custom_components/akvilon_home/AGENTS.md` §9.
2. Клонируем/синхронизируем: `git fetch --all --prune`, проверяем `git status`.
3. От `develop` создаём `feature/<краткое-имя>`.
4. Пишем **маленькие** коммиты в формате `<type>(<scope>): <описание>`:
   `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`.
5. Не переписываем запушенную историю (`git push --force` — только с одобрения владельца).

## 4. Что нужно для сдачи (self-check)

Перед тем как влить ветку, пройти:

- [ ] `python3 -m py_compile custom_components/akvilon_home/*.py` — нет ошибок синтаксиса.
- [ ] Юнит-тесты зелёные: `./scripts/setup_test_env.sh` (первый раз), затем
      `./scripts/run_tests.sh`. На Windows — `scripts/run_tests.ps1`.
- [ ] Логика не ломает загрузку/релоад HA; в журнале нет ошибок интеграции.
- [ ] Нет секретов: реальные IP/DeviceID/PASS/токены заменены на плейсхолдеры
      (см. `RELEASE_POLICY.md` §3).
- [ ] CHANGELOG.md обновлён под новую версию.

## 5. Слияние и релиз

1. Ветка готова и проверена → вливается в приватный `develop`.
2. Владелец проверяет готовность по чеклисту `RELEASE_POLICY.md` §4.
3. `scripts/sanitize.sh` чистит личные данные, `scripts/release.sh` тегирует.
4. Публичный репозиторий получает чистый код; HACS раздаёт его.

Право пушить в `main` и выпускать релизы — у владельца (или явно делегировано).
Слияние в `main` делает только тот, кто лично убедился, что HA работает.

## 6. Безопасность и границы

- Секреты — только плейсхолдеры в коде; `.gitignore` исключает env/secret/*.log.
- Деструктивные и внешние действия (перезапуск HA, релиз, force-push) — только
  с одобрения владельца.
- Не публиковать личные данные жильцов, реальные имена камер-адресов, IP сервера,
  сессионные пароли и токены подписи.

## 7. Если нашли утечку данных

См. `RELEASE_POLICY.md` §7: немедленно удалить/откатить секрет из публичного репо,
повернуть секреты, добавить правило очистки в `sanitize.sh`, зафиксировать случай.
