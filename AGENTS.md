## 1. Что это за проект

**Akvilon InHome** — интеграция для Home Assistant, которая подключается к серверу
здания по **UDP-протоколу** и даёт владельцу квартиры доступ к камерам
видеонаблюдения, калиткам/дверям (открытие по кнопке), счётчикам ГВС/ХВС/отопления,
домофонам и статусу сервера. Это **не официальная** интеграция ЖК «Reka»
(застройщик Аквилон): протокол восстановлен реверс-инжинирингом из трафика
Android-приложения `inHome`.

Это репозиторий — **публичная HACS-копия** (релизы для установки в Home Assistant).
Разработка и обкатка идут в приватном `Gakuzi/akvilon_home`.

## 2. Критичное знание (must-read)

- Сервер здания: `127.0.0.1:19090` (UDP). Реальный IP/порт живут в приватном контексте.
- Пакет: `header(64) + payload + MD5(header[0x2e:0x40] + payload + ASCII(PASS))`.
  В MD5 участвует **ASCII-строка PASS**, а не hex-байты.
- Подписью валидируются команды cmd=3 (subscribe/register); GET (cmd=1) — не проверяется.
- Ключевые каналы: `0x200` подписка, `0x10401` камеры, `0x20401` счётчики,
  `0xE0401` калитки, `0x30401` openCamera, `0x30301` открытие калитки, `0x02020001` регистрация.
- **Сервер отдаёт ~18 тел за одну UDP-сессию** — чтобы собрать все объекты, нужно
  несколько раундов на свежих сессиях и накапливать (см. `protocol.get_list`, параметр `sessions`).
  На каждый входящий пакет слать ACK, иначе сервер останавливает стрим.
- Реальная ситуация (2026-10-08): камер=69, калиток=18-20, счётчиков=4, домофонов=0.
- Видео — кадр по запросу РАБОТАЕТ (openCamera → cameraSettings → UDP-токен → RTP/H.264 → JPEG).
  Живой поток — отдельная задача (см. `docs/ADR/ADR-001-video-frame.md`).

## 3. Цель и приоритеты

Главная цель — **надёжная работающая интеграция**: все камеры, калитки, счётчики
и статус отображались в HA и работали.

1. **Стабильность** — изменением нельзя ломать загрузку/релоад HA.
2. **Полнота данных** — максимум реально доступных объектов с сервера.
3. **Аккуратность** — не выдумывать значения; честно сказать, если не знаем.
4. **Производительность** — не блокировать event-loop HA (долгие операции в executor).
5. **Обратная совместимость** — не ломать существующие сущности в entity_registry.

## 5. Политика веток (git)

> **Текущая модель для параллельной работы (2026-10-10):** в этой HACS-копии
> параллельные фичи ведутся в `feature/*` **от `main`** и сводятся в `main`.
> Ветка `develop` здесь **заморожена** (отстала на 37 коммитов) — не создавать
> от неё ветки и не вливать в неё. Разработка ещё идёт в приватном репо
> (`Gakuzi/akvilon_home`), где свои правила; для этой публичной копии — main-модель.

- `main` стабильный, `develop` интеграционный (заморожен здесь), `feature/*` под задачу, `hotfix/*` от main.
- **Один агент/человек = одна feature-ветка.** Никогда напрямую в `main`/`develop`.
- Формат коммитов: `<type>(<scope>): <описание>` (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`).
- Не переписывать запушенную историю без разрешения.

#«Порядок вызова субагентов»
## Обязательный порядок вызова субагентов перед слиянием

Каждый агент, работающий над фичей, ДОЛЖЕН следовать этой последовательности. Каждый следующий шаг опирается на результат предыдущего. Пропуск шага без уважительной причины — нарушение.

```
1. web-researcher           # этап 1 — только по необходимости внешних данных
2. основной агент (main)    # пишет код фичи в своей ветке, НЕ в main/develop
3. documentation-gate       # навык: задокументировать + коммит по Conventional Commits
4. qa-gatekeeper            # тесты + покрытие + утечки секретов
5. doc-gatekeeper           # гейт документации: README/CHANGELOG/ADR/docstring
6. release-orchestrator     # только перед релизом: сводит ветки, судит сборку
```

### Правила порядка

1. **Документация создаётся ДО коммита** (шаг 3), а не после мержа.
2. **qa-gatekeeper и doc-gatekeeper независимы** — могут вызываться параллельно, но оба ДОЛЖНЫ дать зелёный вердикт до `release-orchestrator`.
3. **release-orchestrator вызывается последним** и только перед релизом/сборкой.
4. **Агент работает в своей ветке**; в `main`/`develop` изменения попадают только через согласованный merge.

### Сокращённый цикл (малая фича)

Для мелких правок допустим укороченный цикл — но шаг документации НЕ пропускается:

```
main (код) → documentation-gate (доки + коммит) → qa-gatekeeper (тесты)
```

`doc-gatekeeper` и `release-orchestrator` запускаются для важных изменений и перед слиянием большого объёма работы.

### Чек-лист готовности к слиянию (все шаги должны быть ✅)

- [ ] Код написан в отдельной фиче-ветке (не в main/develop)
- [ ] Документация создана/обновлена ДО коммита (доки «вместе с кодом»)
- [ ] Коммит по Conventional Commits: `type(scope): description`
- [ ] Тесты зелёные, покрытие не ниже порога (`qa-gatekeeper`: ✅)
- [ ] Секреты не протекают (`qa-gatekeeper`: secrets clean)
- [ ] README/CHANGELOG/ADR/docstring обновлены (`doc-gatekeeper`: ✅)
- [ ] Если что-то не задокументировано — есть явный waiver `Doc-Exempt: <причина>`
- [ ] (только для релиза) `release-orchestrator`: ✅ READY

> **Порог пропуска:** не сдан ни один гейт (тестовый или документационный) — ветка возвращается, а не «вливается с оговорками». Waiver — единственное легальное исключение, и он обязан быть явным.
