# План добычи RTP-видео Аквилон InHome (VIDEO_PLAN.md)

Статус: **видео-поток отложен** — нет pcap реального приложения. Ниже — что
точно известно, что нужно снять и какая связка пакетов откроет поток.

## НОВЫЕ ДАННЫЕ 2026-10-06 (свежий чёрный-ящик, поток feature/video-stream2)

Что удалось ПОДТВЕРДИТЬ эмпирически на живом сервере (`111:69724`, Reka 7
торец дома):

- **cameraSettings ТЕПЕРЬ приходит стабильно**: после `openCamera` на 0x30401
  сервер пушит на канал **0x2030401** (cmd=3 flag=0) JSON: `{name, objectid,
  spropParameter, videoCodec:"264", videoHost:"127.0.0.1", videoPort:5310,
  videoToken:"token_placeholder"}`. SPS/PPS декодируются корректно (SPS
  `67 4d 00 1e e9...`, PPS `68 ea 8f 20`).
- Видео-порт сервера **5310 НЕ отвечает ни на какие UDP-пакеты** (голый токен,
  токен+порт, аквилон-хедер GET/subscribe/openCamera, A7ID+токен) — полный UDP-
  скан 5000-5400, 8000-9000, 10000-11000 дал 0 откликов. Единственный UDP-порт
  сервера, который отвечает, — **19090** (CTRL).
- RTP **не приходит ни на один клиентский порт** (ни на порт CTRL-сокета, ни на
  отдельный RTP-приёмник) ни при каком «пробуждении». Все входящие пакеты —
  только JSON-пуш у cameraSettings/инфо-квартиры/сервера.
- Повторный разбор pcap (cap1..cap4) подтвердил: **ни в одном захвате нет
  ни одного настоящего RTP/H.264 пакета**. Ошибка: кодирование записывает
  `parse` 0x0000 0000 0000 0000 0000 0000 0000 0002 0000 0000 0000 0000 00
  — это ack-заголовок, не видео. Все большие пакеты (997 байт) — это push
  инфо-квартиры (0x3010001), а не видеокадры.
- **Вывод**: сервер держит камеру «открытой» (пушит settings каждые ~0.1с) и
  ждёт ТОЧНЫЙ «подписочный» пакет старта потока, который чёрным-ящиком не
  подобрать. Для его нахождения ОБЯЗАТЕЛЬНО нужен pcap реального приложения
  при живом просмотре (см. рецепт ниже).

Что частично агрегатно реализовано в коде (ветка feature/video-stream2):

- `request_camera_settings` — починен и стабильно отдаёт полные настройки.
- добавлен `start_video_stream` (гипотеза подписки на видео-порт).
- добавлен приёмник `rtp_stream.py` (RtpStream): UDP-слушатель + полная сборка
  RTP/H.264 (одиночные NAL, STAP-A, FU-A) + декод кадра в JPEG через ffmpeg.
  Проверен end-to-end симуляцией: корректно собирает IDR и отдаёт JPEG.
- `camera.py`: `async_camera_image` запускает RtpStream в executor (не блокирует
  HA), `stream_source` возвращает None (чтобы HA не пытался открыть несуществующий
  поток), видео-параметры и rtp_url — в атрибутах.

## Что уже известно (не переоткрывать)

- Протокол управления (CTRL) — UDP, сервер `127.0.0.1:19090`, подпись
  MD5(header[0x2e:0x40] + payload + ASCII(PASS)) с PASS=`PASS_PLACEHOLDER`.
- `device_id=0:0`, `server_id=0:0`, src всегда `0:1`.
- Открытие камеры: `openCamera` на канал `0x30401`, JSON
  `{"id":"<флаг:id>","name":"openCamera"}`.
- Предполагаемый ответ `cameraSettings` приходит на канал `0x2030401` и должен
  содержать `videoPort` / `videoHost` / `videoToken` / `spropParameter`(SPS/PPS)
  / `videoCodec`. **Подтверждён** (см. выше, стабильно возвращается).
- **Критично**: во всех существующих pcap (`/tmp/cap1..cap4.pcap`) захвачен ТОЛЬКО
  CTRL-трафик порта `19090`. НИ ОДНОГО RTP-пакета не снято. Порт 5310, который
  «мелькал» в cap3/cap4 — это **локальный порт клиента** (сокет был пере-забинден
  на 5310), а не видео-порт сервера. То есть реальный видео-обмен ещё ни разу
  не захвачен, и поэтому непонятно, какой пакет на самом деле стартует поток.

## Гипотеза (что ищем)

Видео идёт **UDP/RTP с токеном**:
1. клиент шлёт CTRL `openCamera` (0x30401);
2. сервер присылает настройки/параметры потока (порт + токен + SPS/PPS);
3. клиент шлёт **подписочный/запросный UDP-пакет** на **видео-порт сервера**;
4. сервер стримит RTP (H.264) на UDP-порт клиента.

Пункты 2–4 не подтверждены. Чтобы их закрыть, нужен захват с ПРИЛОЖЕНИЯ.

## Что именно нужно снять в pcap приложения (рецепт)

Цель — добыть три вещи: `videoPort`, `videoToken` и бинарный **подписочный пакет**.

### Оборудование/запуск
- Снять захват на роутере/хосте, где работает приложение аквилон (Android в
  эмуляторе, как раньше — там и собирали протокол).
- Фильтр захвата: `udp and host 127.0.0.1` (весь UDP к серверу, **не только
  порт 19090**). ВАЖНО: предыдущие захваты фильтровались только по 19090,
  поэтому RTP мимо фильтра и ушёл.
- Также обязательно снять **все локальные порты** клиента (RTP придёт на
  случайный UDP-порт клиента), т.е. `udp and host 127.0.0.1` покрывает и это.

### Сценарий (порядок действий в приложении)
1. Запустить `tcpdump -i any -nn -w app.pcap udp and host 127.0.0.1`.
2. В приложении Аквилон открыть **живой просмотр одной камеры** (например
   «Парадная 1-1», id `2:101967`) и подождать 5–10 сек, пока картинка пошла.
3. Остановить захват.

### Что искать в pcap (по убыванию важности)
1. **`cameraSettings`** — JSON с ключами `videoPort`, `videoToken`, `spropParameter`
   (канал 0x2030401). Это подтвердит предполагаемый ответ и даст порт/токен.
   Ищем grep по `videoPort` / `spropParameter` / `videoToken` / `videoHost`.
2. **Подписочный пакет**: исходящий из приложения UDP на **порт, отличный от 19090**
   (например 5000–6000 из статики const.py, или порт из cameraSettings). Это
   `192.168.x.x.<client> -> 127.0.0.1.<video_port>`. Зафиксировать его
   payload (бинарный, обычно заголовок + id сессии/токен).
3. **RTP-поток**: входящие UDP с источника `127.0.0.1.<video_port>` на
   случайный порт клиента. Проверка: payload начинается с `0x80` (RTP), либо
   длинные пакеты 1000+ байт с `0x00 0x00 0x00 0x01` (start code H.264).

### Как связать и проверить
- Если найден `cameraSettings.videoPort` и `videoToken` — это и есть недостающие
  параметры. Тогда подписочный пакет (п.2) обычно = `openCamera`-подобный бинарник
  на видео-порт с токеном, и после него сервер шлёт RTP.
- Если `cameraSettings` НЕ приходит даже от приложения — значит ответ на
  `openCamera` другой канал/структура, и надо декодировать **все** ответы сервера
  на `0x30401` (что именно приходит после openCamera у реального приложения).

## Реализация в интеграции

Готово в ветке feature/video-stream2:
- `AkvilonClient.request_camera_settings` — починен, стабильно получает полный
  cameraSettings (порт/токен/SPS/PPS).
- `AkvilonClient.start_video_stream(cam_id, settings, rtp_port)` — реализован:
  openCamera → settings + лучшая гипотеза «подписочного пакета» на видео-порт.
- `rtp_stream.py` (новый модуль) — `RtpStream`, готовый приёмник RTP/H.264 +
  декод кадра в JPEG через ffmpeg (проверен симуляцией end-to-end).
- `camera.py` — `async_camera_image` через `RtpStream` в executor;
  `stream_source` → None; видео-параметры/rtp_url в атрибутах.

Осталось (нужен pcap приложения):
- точный «подписочный» пакет старта RTP (бинарный payload на видео-порт 5310
  или команда на 19090) — без него сервер не шлёт кадры;
- после его нахождения — подставить в `start_video_stream` и включить
  `stream_source` для настоящего потока.
