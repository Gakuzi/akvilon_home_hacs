## 1. Что это за проект

**Akvilon InHome** — интеграция для Home Assistant, которая подключается к серверу
здания ЖК «Reka» (застройщик Аквилон) по **UDP-протоколу** на `91.122.221.217:19090`.
Она даёт владельцу квартиры №31 доступ к:

- **Камерам** видеонаблюдения жилого комплекса (парадные, лифты, дворы, детские площадки, проезды, калитки)
- **Калиткам** и дверям — открытие по кнопке
- **Счётчикам** — показания ГВС, ХВС, отопления, электричества
- **Домофонам** (если канал данных доступен)
- **Статусу сервера здания** (онлайн/офлайн)

Это **не официальная** интеграция: протокол восстановлен реверс-инжинирингом из
реального трафика Android-приложения `inHome` (версия 4.0.229) и запущен в эмуляторе.

## 2. Ключевая информация о протоколе (CRITICAL)

Сервер здания: **91.122.221.217:19090** (UDP).
Параметры подключения из QR-строки: HOST, PORT, DEVICE_ID (напр. `34:50957`),
SERVER_ID (напр. `7:48390`), PASS (напр. `9c5edcb9`, секрет подписи), SUID (токен).

### Пакет (памятка)
```
header(64 байта) + payload + MD5(header[0x2e:0x40] + payload + ASCII(PASS))
```
- MAGIC = `0x0005000200011004`
- cmd: 1=GET, 2=данные/ACK, 3=command/EVENT
- flag: 0=запрос, 0x02=OK/ACK
- channel: см. ниже

### КЛЮЧЕВЫЕ КАНАЛЫ
| Канал | Назначение |
|-------|-----------|
| `0x200` | подписка на каналы (cmd=3 flag=0x01, повторять каждые ~15с) |
| `0x10401` | камеры (GET-список) |
| `0x20401` | счётчики (GET-список) |
| `0xE0401` | калитки (GET-список) |
| `0x90401` | пользователи (GET-список) |
| `0x10403` | домофоны (GET-список; на этом здании возвращает 0) |
| `0x03010001` | инфо о квартире/правилах доступа |
| `0x30401` | openCamera / closeCamera (JSON с "name":"openCamera") |
| `0x2030401` | cameraSettings (ответ openCamera: videoPort/videoToken/SPS-PPS) |
| `0x30301` | door buttons — ОТКРЫТИЕ КАЛИТКИ (JSON с "action":"open") |
| `0x02020001` | регистрация приложения (обязательна до GET) |

### Секрет подписи (критично!)
- В MD5 участвует **ASCII-строка PASS** (например "9c5edcb9"), а НЕ hex-байты 0x9c 0x5e 0xdc 0xb9.
- Подписью валидируются команды cmd=3 (subscribe/register). GET (cmd=1) — не проверяется.

### GET-список (критично!)
- Payload GET-все = **ровно 32 байта**: u32 тип(1=все, 2=один) + u64 objectId + u32 flag + u64(0) + u64(counter).
- Ответ на GET-ALL: бинарный заголовок `u32 count` + записи по 16 байт `[crc][u64 objectId][u32 flag]`.
- Сервер объявляет в count больше объектов (напр. 69), но стримит JSON-тела частями.
- **Сервер отдаёт только ~18 тел за одну UDP-сессию** — чтобы собрать все 69, не
  обходимо делать несколько раундов на СВЕЖИХ сессиях и накапливать объекты
  (реализовано в `protocol.get_list` с параметром sessions). Не убирай это.
- На каждый входящий пакет нужно слать ACK (cmd=2, flag|=0x02), иначе сервер останавливает стрим.

### Реальная ситуация с данными (2026-10-06)
- `hub.refresh()` получает: камер=69, калиток=18-20, счётчиков=4, домофонов=0.
- Через get_list с накоплением получаются ВСЕ 69 камер с именами.
- Видео-поток RTP камер НЕ запускается: openCamera даёт параметры потока только
  в невоспроизводимой пока последовательности. Подробнее в ветке feature/video-stream.

## 3. Цель и логика разработки

Главная цель — **надёжная работающая интеграция** для владельца квартиры:
все камеры, калитки, счётчики и статус отображались в Home Assistant и работали.

### Приоритеты
1. **Стабильность** — изменением нельзя ломать загрузку/релоад HA.
2. **Полнота данных** — получать максимум реально доступных объектов с сервера.
3. **Аккуратность** — не вставлять выдуманные значения; если не знаем — честно сказать.
4. **Производительность** — не блокировать event-loop HA (долгие операции в executor).
5. **Обратная совместимость** — не ломать существующие сущности в entity_registry.

## 4. Рабочая машина и доступ

- Интеграция лежит на **Raspberry Pi** (SSH-хост `klim`).
- Папка: `/home/pi/homeassistant/custom_components/akvilon_home/`.
- Внутри контейнера HA путь: `/config/custom_components/akvilon_home/`.
- Это же каталог является git-репозиторием (см. раздел 9).
- Можно запускать скрипты/диагностику на Pi: `ssh klim "<cmd>"`.

## 5. Структура файлов

- `__init__.py` — настройка из config entry, async_setup_entry
- `coordinator.py` — AkvilonHub: загрузка камер/калиток/счётчиков/домофонов
- `protocol.py` — UDP-клиент AkvilonClient (ядро протокола)
- `camera.py` — платформа camera
- `button.py` — кнопки открытия калиток
- `sensor.py` — счётчики + состояние калиток
- `binary_sensor.py` — онлайн-статус сервера
- `config_flow.py` — мастер настройки (QR-строка)
- `const.py` — константы, каналы, справочники
- `manifest.json` — домен, версия (1.1.0), HA-совместимость
- `services.yaml`, `strings.json` — сервисы и переводы

## 6. Тестирование

После запуска HA в журнале ожидаемо увидеть:
```
Аквилон: setup_entry name='Аквилон InHome' ...
Аквилон: обновлено камер=69, калиток=18, счётчиков=4, домофонов=0
Аквилон: добавлено N камер из сервера
```
Если банк не получен — в логе: `Аквилон: банк cameras не получен: <error>`.

## 7. Политика веток (git)

Репозиторий: https://github.com/Gakuzi/akvilon_home.git (origin).

- `main` — стабильная версия. Сюда попадает ТОЛЬКО проверенный код после слияния.
- `develop` — интеграционная ветка разработки. Общая точка сборки.
- `feature/*` — ветки под конкретную задачу/фичу. Создаются от develop.
- `hotfix/*` — срочные исправления от main.

> Список текущих веток смотри через `git branch -a` / `git ls-remote origin`.

## 8. Ограничения и честность

- НЕ выдумывай URL, порты, значения, которых нет в данных сервера.
- Если сервер не отдаёт объект (например домофоны на канале 0x10403 дают 0) —
  это факт сервера, не баг; прогони диагностику прежде чем "чинить".
- Изменение .storage (entity_registry/config_entries) вручную рискованно —
  предпочитай пересоздание через config flow.
- Видео-RTP не запускается без реального pcap приложения inHome — об этом
  подробнее в feature/video-stream. Не трать время на бесконечные комбинации
  без данных; нужен захват трафика.

## 9. ПОРЯДОК РАЗРАБОТКИ (обязателен для всех агентов)

Это главный раздел. Его соблюдают и люди, и агенты.

### 9.1. Перед началом работы (первое действие)
Всегда выполняй в этой последовательности:

```bash
# 1) Зайти в репозиторий
cd /home/pi/homeassistant/custom_components/akvilon_home

# 2) Прочитать инструкции (ОБЯЗАТЕЛЬНО)
cat AGENTS.md README.md

# 3) Понять состояние веток
git fetch --all --prune
git branch -a
git log --oneline -5 origin/develop

# 4) Определиться, в какой ветке работаешь
#    - Если решаешь отдельную задачу -> создать feature-ветку от develop
#    - Если продолжаешь чужую работу -> переключиться на существующую feature-ветку
git status        # чтобы не затоптать чужие незакоммиченные изменения
```

### 9.2. Создание feature-ветки (если тебе поручили новую задачу)

```bash
cd /home/pi/homeassistant/custom_components/akvilon_home
git checkout develop        # уйти от старой ветки
git pull origin develop     # обновить
git checkout -b feature/<краткое-имя>   # новая ветка от develop
```

Имя ветки — осмысленное: `feature/video-stream`, `feature/cleanup-entities`,
`fix/meter-values`, и т.п.

### 9.3. Во время разработки

- Делай МАЛЕНЬКИЕ коммиты с осмысленными сообщениями.
- Формат сообщений: `<type>(<scope>): <описание>`
  - `feat: ...` — новая функциональность
  - `fix: ...` — исправление
  - `docs: ...` — документация
  - `refactor: ...` — рефакторинг без изменения поведения
  - `test: ...` — тесты
- Коммить часто: написал кусок — закоммить.
- Между коммитами можно пушить свою ветку, чтобы не потерять работу:
  ```bash
  git add -A && git commit -m "feat: ..."
  git push -u origin feature/<имя>     # один раз; дальше просто git push
  ```

### 9.4. Параллельная работа нескольких агентов (важно!)

Множество агентов могут работать одновременно. Чтобы не мешать друг другу:

- **Каждый агент работает ИСКЛЮЧИТЕЛЬНО в своей ветке** `feature/*`.
- **НИКОГДА** не коммить напрямую в `develop` или `main`.
- **НИКОГДА** не работай в незакоммиченной рабочей копии, если на ней уже есть
  чужие изменения (проверяй `git status`).
- Перед каждым действием `git pull origin <своя-ветка>`, чтобы подтянуть
  изменения, если кто-то ещё пушил в ту же ветку.
- Если два агента захотели одну и ту же ветку — сначала `git pull`, потом не
  пытайся перезаписать; при конфликте писать в обсуждение.

### 9.5. Завершение задачи и слияние

Когда твоя ветка готова и проверена:

```bash
cd /home/pi/homeassistant/custom_components/akvilon_home
# 1) Убедиться, что в ветке всё закоммичено и синхронизировано
git status          # чисто
git push origin feature/<имя>

# 2) Обновить develop и влиться в него
git checkout develop
git pull origin develop
git merge feature/<имя>          # либо --no-ff для явной записи
git push origin develop

# 3) Только после того, как develop стабилен (HA стартует, сущности живые),
#    влить в main
git checkout main
git pull origin main
git merge develop
git push origin main
```

Правило: **merge в main делает только тот, кто лично убедился, что HA работает**
(перезапустил контейнер и проверил журнал).

### 9.6. Проверка после любых изменений (обязательно)

```bash
cd /home/pi/homeassistant/custom_components/akvilon_home
python3 -m py_compile *.py                 # синтаксис
ssh klim "docker restart homeassistant"    # применяем
sleep 60
ssh klim 'docker logs homeassistant --since 2m 2>&1 | grep -iE "аквилон|akvilon|ERROR"'
```

Если в логе ошибки — исправь их в СВОЕЙ feature-ветке и повтори. Не вливай
сломанный код в develop/main.

### 9.7. Откат при ошибке

Если что-то пошло не так на своей feature-ветке — безопасный откат:
```bash
git checkout <хороший-коммит> -- <файл>   # вернуть конкретный файл
git reset --soft HEAD~1                    # отменить последний коммит, сохранив изменения
```
Никогда не используй `git reset --hard` без крайней необходимости и без
сообщения пользователю.

## 10. Пример: как агент начинает работу над задачей

Допустим, тебе дали задачу «починить загрузку всех камер»:

1. `cd /home/pi/homeassistant/custom_components/akvilon_home`
2. `cat AGENTS.md README.md` — читаешь правила.
3. `git fetch --all && git checkout develop && git pull origin develop`
4. `git checkout -b feature/fix-all-cameras`
5. Правишь `protocol.py`/`coordinator.py` маленькими коммитами.
6. `python3 -m py_compile *.py` — ошибок нет.
7. `ssh klim "docker restart homeassistant"` и проверяешь журнал.
8. `git add -A && git commit -m "fix: получение всех камер" && git push -u origin feature/fix-all-cameras`
9. Сообщаешь пользователю/менеджеру, что ветка готова к слиянию.
