## 2. Что выяснено по домофонам и тарифам (реальные данные)

### Домофоны
- **Отдельного канала домофонов нет.** `CH_INTERCOM=0x10403` стабильно возвращает 0
  устройств. Просканировал соседние каналы (`0x10401..0x10406`, `0x20402/0x20403/0x2040e`,
  `0xE0402`, `0x90402`, `0x1040e`, `0x10409`, `0x3010001`, `0x3020001`) — устройства
  даёт **только `0x10401` (камеры, 69 шт.)**. Значит отдельного «списка переговорок» на этом
  сервере нет.
- **Домофон = калитка/вход, у которой проставлен реальный `cameraId`** («калитка+камера»).
  Из 20 калиток на момент опроса **8 имеют cameraId** → это и есть домофоны:
  - 1:80650 «Калитка 14» ← cam 1:79725 «Калитка 8, Река 5»
  - 16:83076 «Калитка 18» ← cam 1:79653 «Калитка 12, Река 7»
  - 746:87893 «Калитка 16» ← cam 1:79690 «Калитка 10, Река 6»
  - 178:87931 «Калитка 15» ← cam 1:79712 «Калитка 9, Река 6»
  - 559:89013 «Калитка 12» ← cam 1:80657 «Калитка 6, Река 4»
  - 950:89653 «Калитка 17» ← cam 1:79673 «Калитка 11, Река 7»
  - **1:101908 «Reka 4, Проход 1-2» ← cam 3:101885 «Парадная 1-2»** (вход в подъезд)
  - **2:101911 «Reka4, Prohod 1-1» ← cam 2:101967 «Парадная 1-1»** (вход в подъезд)
- «2 входа в подъезд» — это два последних прохода (Reka 4 Проход 1-1/1-2) с камерами «Парадная 1-1/1-2». Оба попадают под правило «калитка с cameraId».
- Связка по objectid реализована в `AkvilonHub.intercom_link()`: `gate_id`, `gate_name`, `gate_status`, `camera_id`, `camera_name`, `controller_id`.

### Тарифы счётчиков
- Счётчиков 4: ГВС (resourceType 3), ХВС (resourceType 2), Отопление (resourceType 4), Электричество (resourceType 1).
- **Электричество** приходит одним объектом: `current` = JSON-строка
  `{"dt":"...","value":9992.95,"values":[7255.78, 2737.17, 0, 0],"unit":"кВт*ч"}`.
  - `value` = сумма тарифов: 7255.78 + 2737.17 = **9992.95**. ✓
  - `values[0]` = тариф T1 = 7255.78 → **«День»** (значение больше — типичная раскладка).
  - `values[1]` = тариф T2 = 2737.17 → **«Ночь»**.
  - `values[2],[3]` = 0 (не используются).
- Создаются: основной сенсор (Итого) + 2 тарифных `День`/`Ночь`.
- **Допущение к проверке**: сервер не подписывает, какой регистр день, какой ночь.
  Взято стандартное T1=День, T2=Ночь по величине показаний. При необходимости легко
  поменять в `sensor.py` (индекс/подпись).

## 4. Открытые вопросы
1. **Какой тариф «день», какой «ночь»** у электричества — сервер не маркирует; принято T1=День, T2=Ночь. Перепроверить по реальному приложению.
2. **Статус калитки**: сервер отдаёт только `controllerStatus` (0/1) и `enabled`, события «открыта/закрыта» в списке нет. Сенсор калитки/домофона показывает online/offline контроллера, а не открыта/закрыта. Если нужен реальный статус двери — надо ловить EVENT-сообщения по каналу `0xE0401`/`0x200` во время опроса (будущая работа).
3. **RTP-видео**: полностью отложено — нужен pcap с реального приложения (см. `VIDEO_PLAN.md`);
   `cameraSettings` стабильно не подтверждён, во всех текущих pcap только CTRL-порт 19090, RTP не захвачен.
4. **Количество домофонов плавает** (8 в свежих опросах; ранее в дампе «Калитка 13» имела cameraId=2:79754). Зависит от живости сервера; вывод динамический — это фича, не баг.
5. **`hub.get_camera_settings`/`camera_video_url`** оставлены, но теперь НИЧЕГО на event loop их не вызывает. Если Поток B захочет видео-настройки — вызывать ТОЛЬКО из executor с таймаутом, чтобы не возвращались блокирующие `time.sleep`.
